### Data freshness (planned 2026-10-31)

Goal: the collapsed rows as current as possible, and anything not yet fully updated obviously so. Found in a review of the retrieval flow: one changed PR made the quick check's fast-follow refetch the whole repo, and the 15-minute sweep refetched every listed PR (about 6 `gh` calls each; `VIEW_PRS_SKIP_UNCHANGED` row reuse is off by default); what GitHub changes without moving `updatedAt` (CI, mergeability, viewed files, possibly resolved threads) waited for that sweep, unmarked; each row written rewrote and backed up the whole data file; merged/closed PRs were fetched like open ones.

- [x] 1. Live summary: a GraphQL listing of each repo's open PRs with every quick check, laid over the rows (see README's automatic background refresh, and `DATA_SCHEMA.md`). Rows carry `data.live`; the polled data version includes it and the PRs queued for update.
- [x] 2. Refresh only the PRs that changed: the script's `--prs`, used by the fast-follow (which then keeps the full sweep's time) and the merged/closed drain; a repo with more than 25 queued gets its full refresh. A run of chosen PRs (`--prs`, and now `-p`) keeps each row's run stamp and the new `lastFullRun`, so `Last run rows` still means the last full run (`lastRun` stays every run's, for the header). `--prs` fails, keeping them queued, when a chosen PR can't be fetched. Then: the manual cooldown holds off only that repo's full refreshes after a manual run of the whole repo (a run of one PR used to hold off every refresh everywhere for 15 minutes); a quick check of entered numbers, or a manual run of one PR, settles only those numbers in the queue; a row a run of chosen PRs adds joins `Last run rows`.
  - Open: a run of chosen PRs that fails because one can't be fetched counts toward the repo's circuit breaker, so a few in a row pause its background updates (full refreshes too) until a full refresh succeeds. Unlikely - the numbers come from GitHub's listing - but a missing PR could be dropped from the queue instead of failing the run.
- [x] 3. The sweep as a safety net: a full run reuses a row whose `updatedAt` matches (and its local state - acks, filters - see README's Reusing unchanged rows); open rows are fetched in full again after 4 hours (`VIEW_PRS_OPEN_REVALIDATE_SECONDS`); merged/closed rows only when they change, without their viewed files (after their first merged/closed row). A reused row keeps `fetchedAt`, so the live summary still applies to it. A manual `Run script` still fetches everything.
  - After review (2026-11-02): resolving a thread doesn't move `updatedAt`, so a reused open row kept its threads, and the status reason from them, for up to 4 hours (15 minutes before reuse); the quick check now also queues an open PR whose unresolved-thread count differs from a newer listing's (`findPrsWithChangedThreads`), and the targeted refresh refetches it. The live summary pages in creation order: in update order, a PR updated while the pages were read was skipped, and a complete listing without it marked it `No longer open`.
  - Left: a changed merged/closed PR's details call still asks for CI and mergeability (same call, so no saving in calls); the old fingerprint-based reuse (never effective - its prefetches don't run, see 4) is gone.
- [x] 4. Write path: one backup per run, before its first row, not one per row (and none with a quick check); a row is written in one `jq` pass, without a second to check it. The reuse check reads a per-run snapshot of the repo's rows, one small file each, instead of the whole data file twice per PR, and works out the local state key in the same `jq` (the key is now a checksum of what every PR shares plus the PR's marks, so every row was fetched once more after this). The four parallel prefetches that ran `bash -c 'fetch_..._json'` without those functions (review threads, review comments, review links, viewed files) run as background subshells now, so they fetch; `--jobs` is shared among the prefetches run together (each took `--jobs`, which once they all worked meant up to 36 `gh` calls at once against the server's budget of 4 a refresh). A state file is replaced by a rename beside it, not a move from the temp folder (another drive here, so a copy over the file the server could read half-written). `print_row` takes one `jq`, not nine. The details call's CI data was already used for a fetched row (step 3 fetches CI separately only for reused open rows). On cli/cli with 12 PRs: a full fetch 158s → 86s, a run reusing every row 43s → 30s.
  - After review (2026-11-02): a failed review-thread request returned no threads (bash clears `set -e` inside `$(...)`), the prefetch cached that, and the row was written without its threads - kept so while full runs reused it. A failed thread or details fetch now fails, caches nothing, and the run keeps the PR's stored row (`note_unfetched_pr`): a run of chosen PRs fails naming it, a full run says so. Backups: the newest 50, plus the newest of each day until 7 days have one (`STATE_BACKUP_DAILY_DAYS`) - a run every few minutes left only the last few hours.
  - Rows and notes are keyed by `repo#number` (2026-11-02): keyed by the bare number, two repos' PRs with the same number replaced each other's rows and shared notes. The script migrates the data file each run (`ensure_pr_state_store`), the server reads either kind and migrates notes (`view-prs-pr-keys.js`), and the notes route takes the repo. `data-processing-helpers.js` (an unused copy of `readViewPrsData`'s helpers, required only by its own test) wasn't changed, and was removed on 2026-11-03.
  - Left: what's left is mostly a process per field per row (decoding the listing, `isDraft`, `status`, `baseline`, the filters) - step 6's territory; each row still rewrites the whole data file.
- [x] Tests: `src/script/integration-tests/check-open-pr-updates.test.sh` passes as a whole, and `check-open-pr-updates.sh-tests*.test.js` run all of it in Jest, one group per test, over three files so the full-run group (about 4.5 minutes) runs alongside the rest; a failing group shows the end of the script's output, and a hung one is killed. CI's Linux test job had failed since `28ee9ed` on the `--prs` and row-reuse groups, likely because the tests ran the script with `sh`, which on Ubuntu is dash (Git Bash's `sh` is bash); they use `bash` now. What was wrong was the tests, not the script: two detail fixtures (PRs 109 and 210) ended their heredocs with an indented `JSON`, so each swallowed the fixtures after it (207, 200 and others fell back to an empty detail); the timeline, activity and review-thread assertions read fields the row now keeps in its PR detail file; `base64` wrapped the encoded listings the stale and quick-check collections read; the reconcile test's mock `gh` used the sourced script's exported `jq()` without its `JQ_BIN`; and the full runs had no `--repo`. The tests also wrote PR detail files and state backups into the real `data/` (`owner_repo__pr-*.json`, `user-state.json.*.bak`); they now keep `DATA_DIR` in their temporary folder (they also read the real `user-defaults.json`'s change filters and merge-commit rules). `ONLY_TESTS` rejects a name with no test function, and `cache_freshness`' row-reuse checks, which couldn't fail (its stored rows lack what reuse needs), are gone; the Jest reuse tests cover runs of chosen PRs instead.
  - Left: `run_all_tests` runs inside `if`, so `set -e` is off in every test - a failing command that isn't an assertion (a jq error, say) doesn't fail its test. Turning it on may surface old failures that never mattered.
- [x] 5. Show freshness (see README's Freshness): each open/draft row's Activity tooltip has when its summary was confirmed (its repo's listing, or its fetch) and when its details were fetched; it's stale (dotted ages) after about two of its repo's quick-check intervals unconfirmed, or while its repo's listing fails - the data meta now gives each repo's interval. `Details updating` under the title, and dimmed Activity ages, while `data.live.detailsBehind` or queued; `No longer open` when a complete listing lacks it. The header pill says when the repos were checked (`Checked 3m ago`, each repo on hover). Data changes are pushed: while a page is connected, the events route checks the data version every 3s (`VIEW_PRS_EVENTS_DATA_WATCH_INTERVAL_MS`) and sends `data-changed` when it moves; the page fetches one change at a time, and polls every 5 minutes instead of 30s while connected. A poll that found no changed rows used to drop the new data meta, so a listing never reached the page until a row changed. A reused open row's CI is stamped (`ciFetchedAt`), so an older listing no longer replaces the CI the sweep just fetched. The old per-row "last checked" (the run stamp, which runs of chosen PRs no longer move) is gone. After review: a full run reusing a row confirms its summary too (`ciFetchedAt`, `updatedAt`), so unlisted rows (a repo over 500 open PRs, the live summary off) aren't stale for the 4 hours `fetchedAt` stays; the row versions the page compares include `fetchedAt`/`ciFetchedAt` (a run of chosen PRs can move only those); a repo with no background updates reads as not checked automatically, not stale; and pushed changes no longer overwrite the status line (only a new run does).
  - After a second review: a repo whose background updates are paused (its circuit breaker) says until when, rather than just stale - the data meta's new `backgroundUpdates` gives every repo checked in the background its interval and pause, listed or not, so a custom interval also applies with the live summary off; a reused row whose CI fetch failed isn't confirmed by the run's stamp (only rows from before `ciFetchedAt` are); and the page checks for changes on its first connection too, once its data has loaded (the watcher only pushes changes from when a connection opens).
  - Left: the data watcher makes a busy run push every few seconds, and each push reads the whole data file for the manifest (as each 30s poll did); a server-side row-version cache would make that cheap. The Review cell's approvals aren't marked while details are behind - only the Activity ages and the title's chip.
- [x] 6. Move the detail computation from bash to Node: `compute_pr_state_json`'s computation (with its helpers, about 1,100 lines of bash and jq) is `src/script/compute-pr-row.js`, a pure function from what the script fetched to the row, run once a row. The script still fetches, reads the user state, clears an ack and writes the detail file. A parity test ran the old jq and the new path on generated cases (ties in time, fractional seconds, non-ASCII names, review URLs, merge commits, invalid patterns) and required the same row JSON, key order included, and the same ack decision: 302 cases matched. It was retired, with the jq copy it ran, once the port shipped and the rows began to change on purpose (below). Computing a row: 3.5s with jq, 0.6s with Node (fetches not included; Windows). The script needs Node: the server passes its own (`VIEW_PRS_NODE`); run standalone, `node` on `PATH`.
  - Found on the way: the viewer's own commits never counted as their last activity (the jq read `.committedDate` from the commit's author, which has none) - fixed. On Windows `jq.exe -r` wrote the activity timeline summary's line breaks as CRLF - the Node one has LF everywhere.
  - Since: commits after the one the viewer's latest review was on count as new, though made before it (a commit's date is when it was made, not pushed) - not when an ack is the baseline. On the viewer's own PR, a review that requests changes or has a body marks it CHANGED (`review`); approvals and the empty reviews GitHub wraps inline comments in don't.
