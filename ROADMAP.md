### Data freshness (planned 2026-10-31)

Goal: the collapsed rows as current as possible, and anything not yet fully updated obviously so. Found in a review of the retrieval flow: one changed PR made the quick check's fast-follow refetch the whole repo, and the 15-minute sweep refetched every listed PR (about 6 `gh` calls each; `VIEW_PRS_SKIP_UNCHANGED` row reuse is off by default); what GitHub changes without moving `updatedAt` (CI, mergeability, viewed files, possibly resolved threads) waited for that sweep, unmarked; each row written rewrote and backed up the whole data file; merged/closed PRs were fetched like open ones.

- [x] 1. Live summary: a GraphQL listing of each repo's open PRs with every quick check, laid over the rows (see README's automatic background refresh, and `DATA_SCHEMA.md`). Rows carry `data.live`; the polled data version includes it and the PRs queued for update.
- [x] 2. Refresh only the PRs that changed: the script's `--prs`, used by the fast-follow (which then keeps the full sweep's time) and the merged/closed drain; a repo with more than 25 queued gets its full refresh. A run of chosen PRs (`--prs`, and now `-p`) keeps each row's run stamp and the new `lastFullRun`, so `Last run rows` still means the last full run (`lastRun` stays every run's, for the header). `--prs` fails, keeping them queued, when a chosen PR can't be fetched. Then: the manual cooldown holds off only that repo's full refreshes after a manual run of the whole repo (a run of one PR used to hold off every refresh everywhere for 15 minutes); a quick check of entered numbers, or a manual run of one PR, settles only those numbers in the queue; a row a run of chosen PRs adds joins `Last run rows`.
  - Open: a run of chosen PRs that fails because one can't be fetched counts toward the repo's circuit breaker, so a few in a row pause its background updates (full refreshes too) until a full refresh succeeds. Unlikely - the numbers come from GitHub's listing - but a missing PR could be dropped from the queue instead of failing the run.
- [x] 3. The sweep as a safety net: a full run reuses a row whose `updatedAt` matches (and its local state - acks, filters - see README's Reusing unchanged rows); open rows are fetched in full again after 4 hours (`VIEW_PRS_OPEN_REVALIDATE_SECONDS`); merged/closed rows only when they change, without their viewed files (after their first merged/closed row). A reused row keeps `fetchedAt`, so the live summary still applies to it. A manual `Run script` still fetches everything.
  - After review (2026-11-02): resolving a thread doesn't move `updatedAt`, so a reused open row kept its threads, and the status reason from them, for up to 4 hours (15 minutes before reuse); the quick check now also queues an open PR whose unresolved-thread count differs from a newer listing's (`findPrsWithChangedThreads`), and the targeted refresh refetches it. The live summary pages in creation order: in update order, a PR updated while the pages were read was skipped, and a complete listing without it marked it `No longer open`.
  - Left: a changed merged/closed PR's details call still asks for CI and mergeability (same call, so no saving in calls); the old fingerprint-based reuse (never effective - its prefetches don't run, see 4) is gone.
